# 生成式 UI（GenUI）调查报告

> 研究对象：OpenTiny genui-sdk 及本地 playground
> 调查日期：2026-08-20
> 数据来源：本地实机部署、源码分析、LLM 端点实测

---

## 1. 摘要

生成式 UI（GenUI）的本质是：**用自然语言让 LLM 产出声明式 Schema，再由前端渲染器把 Schema 渲染成真实页面**。它把"开发页面"从"写代码"变成"描述需求"。

本报告基于本地跑通的 playground 实测，从**成本、使用边界、效果**三个维度给出结论，并正面回应"有了 LLM，生成式 UI 是不是鸡肋"的质疑。

**核心结论先行**：
- 生成式 UI **不是通用替代品**，是一个**特定场景工具**——适合"表单 / 展示 / 报表"类、长尾多变、低交互复杂度的页面。
- 它的价值在**对话式迭代**与**Schema 资产化**（可存储、可复用、可二次编辑），而非"更快写出页面"。
- 如果目标是"一次性写出一个固定页面"，直接让 LLM 写代码**更快更省**；此时生成式 UI 确实鸡肋。
- 如果场景是"页面需求频繁变化、需要反复改、要长期维护"，生成式 UI 有明显价值。

---

## 2. 生成式 UI 是什么：两阶段模型（关键）

务必区分两个阶段，二者成本与性质完全不同：

| 维度 | 生成阶段（设计期） | 运行阶段（交付期） |
|---|---|---|
| LLM 是否在场 | **是**，负责产出/修改 Schema | **否**，页面交付后完全无 LLM |
| 产物 | JSON Schema（componentName 节点树） | 渲染器把 Schema 渲染为 DOM |
| 变更方式 | 对话修改 Schema（重新生成） | 无变更，或改 Schema 后重新发布 |
| 依赖 | LLM 服务 + 物料库（组件描述） | 纯前端 JS，业务逻辑调用户自己的后端 |
| 成本 | 每次生成/修改消耗 Token | 约等于零（无 API 调用） |

> 重要：运行阶段的页面是**固定的、纯前端的**，运行时业务后端是用户自己的系统，与生成式 UI 无关。生成式 UI 只负责"把页面造出来"这一步。

---

## 3. 成本分析

### 3.1 Token 成本（实测数据）

在本地 playground 实测，模型 `gpt-5.6-luna`（OpenAI 兼容端点）：

| 场景 | prompt_tokens | completion_tokens | total_tokens |
|---|---|---|---|
| 裸调用：让 LLM 生成登录表单 | 33 | 278 | **311** |
| playground 完整链路：生成员工表单页面 | 21,351 | 2,664 | **24,015** |

**关键发现**：走完整链路时，prompt 高达 21K tokens——**绝大部分是系统提示词里的协议说明 + 物料库组件描述**，用户实际说的话只占几十个 token。

#### 换算成钱（参考主流模型定价）

| 模型档位 | 假设单价（输入/输出，$/1M） | 单次生成成本（约 24K total） |
|---|---|---|
| 便宜档（类 DeepSeek） | $0.3 / $1 | **≈ $0.009**（约 6 分人民币） |
| 中档（类 GPT-4o-mini） | $0.6 / $2 | **≈ $0.018**（约 1 角 3 分） |
| 贵档（类 GPT-4o） | $2.5 / $10 | **≈ $0.08**（约 5 角 8 分） |

> 结论：**单次生成的 Token 成本本身很低**（几分钱到几毛钱），但注意这是"一次生成"。对话式迭代每多聊一轮，prompt 会把前面的对话历史继续带上，成本随轮次近似线性增长。一次含 5 轮修改的完整设计会话，约等于 5 次生成的量。

### 3.2 基础设施成本

| 项目 | 说明 | 成本量级 |
|---|---|---|
| LLM 服务 | 内网部署推理服务（vLLM/Ollama 等）或云端 API | GPU 或按量付费，占大头 |
| 生成式 UI 框架本身 | genui-sdk 开源，本地起 playground 即可 | **0 元** |
| 物料库 | 内置 OpenTiny 组件已齐备；自研组件需注册+写描述 | 一次性人力 |

### 3.3 人力/维护成本

- **物料库维护**：每新增一个自研组件，需写一份 `IGenPromptComponent` 格式的描述（properties/events/ref），让 LLM 能正确引用。这是长期维护点。
- **Prompt 调优**：不同模型对 Schema 协议的遵循度不同，可能需要针对模型微调系统提示词（如 `supportJsonFormat`、`specificPrompt`）。
- **与传统开发对比**：传统开发是"写页面 + 测 + 改"；生成式 UI 是"调对话 + 验 Schema + 改"。对简单页面，传统开发更快；对多变页面，生成式 UI 免去了"每次改动都改代码"。

## 4. 使用边界

### 4.1 适合的场景

| 场景类型 | 特征 | 例子 |
|---|---|---|
| **表单类** | 字段多、规则标准、交互单一 | 注册/登记/申请/配置类表单 |
| **展示类** | 只读、数据驱动、排版规整 | 详情页、列表、报表、看板 |
| **长尾多变页面** | 数量大、单页低频、改版频繁 | 内部管理系统、运营活动页 |
| **对话式 UI** | 页面随对话上下文演化 | AI 助手内嵌的配置/操作面板 |
| **低代码交付** | 让非程序员自己生成页面 | 业务人员自助搭建 |

### 4.2 不适合的场景

| 场景类型 | 原因 |
|---|---|
| **重型交互**（画布、拖拽、富文本、流程图） | Schema 节点树表达不了复杂交互态，需自定义组件兜底，成本逼近传统开发 |
| **复杂状态/联动** | 强业务逻辑应写在运行时 JS，塞进 Schema 会失控 |
| **性能敏感**（大数据表格、虚拟滚动） | 通用渲染器性能不如手写优化 |
| **像素级高保真页面** | LLM 生成排版难以精确控制，最终仍要人改 |

### 4.3 边界判定准则

问自己三个问题：
1. **页面交互复杂度**：是否只是"填表单 / 看数据"？→ 是则适合
2. **页面变更频率**：是否经常改字段、改布局？→ 是则适合
3. **是否需要长期维护资产**：Schema 要不要沉淀复用？→ 是则适合

三个都答"是" → 生成式 UI 价值大；都答"否" → 直接写代码。

## 5. 效果分析

### 5.1 效率

- **开发速度**：从"写代码"变为"描述需求"，一个表单页从 30 分钟降到 1-2 分钟（含对话迭代）。
- **改版速度**：改字段/改布局 = 对话修改 Schema，不用翻代码。这是最大红利。
- **新上手成本**：非前端人员（业务、测试、运营）也能生成可用页面。

### 5.2 质量与一致性

- **组件一致性**：受物料库约束，生成的页面用的是统一的 Tiny 组件，风格天然一致（这点优于"LLM 直接写 HTML/CSS"）。
- **质量不确定性**：LLM 可能生成不符合协议的 Schema，需要人工校验；复杂页面仍需前端兜底调整。

### 5.3 可维护性 / 资产化

- Schema 是**纯数据**：可存数据库、可版本控制、可服务端动态下发、可二次编辑。
- 同一个 Schema 可被不同框架渲染（vue/angular），换肤、换端成本低。
- 这是"LLM 直接生成 .vue/.jsx 文件"做不到的——代码是一次性的，Schema 是资产。

### 5.4 体验局限

- 对话式生成有**不可控感**：同一句话每次结果可能不同，需要确认。
- 复杂页面生成成功率下降，迭代轮次变多，成本上升。

## 6. 正面回应："有了 LLM，生成式 UI 是不是鸡肋？"

这是核心问题。诚实回答：**部分场景是，部分场景不是。**

### 6.1 为什么感觉鸡肋？（合理之处）

- **LLM 已经能直接写代码**。对"一次性、固定的页面"，让 LLM 直接写 Vue/React 组件，比生成 Schema 再渲染，链路更短、更可控、Token 更少（少了大段系统提示词）。
- **多一层抽象，多一层不确定性**。Schema 协议本身需要学习、校验、排错；如果只为了"出页面"，这层抽象是负担。
- **运行阶段其实不需要 LLM 的智能**。页面一旦固定，就是普通前端页面——此时"生成式"的帽子没有任何加持。

所以：**如果你只是想把一个页面做出来，而且不太会再改，那用 LLM 直接写代码就够了，生成式 UI 是鸡肋。**

### 6.2 为什么又不鸡肋？（价值所在）

生成式 UI 真正值钱的地方，不在"生成那一刻"，而在：

1. **页面是"活"的**。Schema 是数据资产：存起来、改起来、复用它。传统代码是"死"的：每次改动都要动代码、走发布。
2. **对话式迭代**。用户说"再加个邮箱字段""按钮改成红色"，对话里就改完了。这是"描述需求"而非"改代码"。
3. **与业务运行时解耦**。生成阶段用完 LLM 就退场，运行阶段纯前端、零依赖、低风险，页面交付后 LLM 挂了页面照样跑。
4. **非程序员可用**。让业务/运营自助生成页面，把"要资源排期"变成"自己搭"。

### 6.3 一句话判断

> **生成式 UI 的价值 = 降低"页面反复修改"的边际成本；它不擅长降低"页面首次产出"的成本。**

- 首次产出：LLM 写代码 ≈ LLM 生成 Schema（甚至前者更快）→ 此维度鸡肋
- 反复修改：改 Schema（对话）≫ 改代码 → 此维度价值显著
- 资产沉淀 / 动态下发：Schema 完胜 → 此维度不可替代

---

## 7. 结论与建议

### 7.1 结论

1. 生成式 UI **不是更快的写代码工具，而是"页面资产化 + 对话式迭代"工具**。
2. 它适合**表单、展示、报表**类、**长尾多变**、**低交互复杂度**的页面（内部系统、运营配置、AI 应用对话 UI）。
3. 它**不适合**重型交互、复杂状态、性能敏感页面。
4. 单次 Token 成本低（约 0.06~0.6 元/次），对话式迭代成本随轮次线性增长，整体仍远低于人力成本。
5. **运行阶段完全无 LLM**，页面交付后是纯前端，无运行时 API 成本、无 LLM 故障风险——这是它区别于"LLM 直接写代码 + 运行时仍调 LLM"的关键优势。

### 7.2 建议

- **若追求"一次性快速出页面"**：直接用 LLM 写代码，别用生成式 UI。
- **若页面会反复变、要沉淀复用、或给非程序员用**：值得投入生成式 UI。
- **混合使用**：高价值、低频改动的页面走传统开发；长尾、多变的表单/展示页走生成式 UI，两者共存。

### 7.3 补充：什么情况下值得再关注

- 若后续引入**运行时 Schema 动态下发 + 无代码配置后台**，生成式 UI 的价值会放大（页面即数据）。
- 若 LLM 对 Schema 协议的遵循度足够稳定（可配合 `supportJsonFormat` / 严格校验），生成成功率提升，鸡肋感会显著下降。
